Flash the Klingelbox firmware onto an ESP32-S3 straight from this page — no ESP-IDF, no Python, nothing installed. Die Klingel, lokal und ohne Cloud.

This browser cannot flash. Use Chrome or Edge on a desktop computer (Windows, macOS or Linux). The Web Serial API this page needs does not exist in Safari, does not exist in Firefox, and does not exist in any browser on iOS or Android — including Chrome on those platforms. On an unsupported device, use the manual idf.py route instead.
A full-image flash factory-resets the device. The release image spans the whole flash, so everything is reset: Wi-Fi credentials, hostname, MQTT settings, your learned signals and your whole node graph. To update a Klingelbox that already works, use OTA instead (Firmware in the device's web UI, or POST /api/ota) — that keeps all configuration.

Release images are mirrored into this site by CI, because GitHub's own release downloads cannot be fetched by a web page. Every download is checked against its published size and SHA-256 before a single byte is written to your board.

For self-built images — including the 4 MB ESP32-S3 Zero build, which you produce with SDKCONFIG_DEFAULTS="sdkconfig.defaults;sdkconfig.defaults.4mb". A merged image (klingelbox-esp32s3-full.bin) goes at 0x0. The app-only image (klingelbox.bin) and the web-UI image (storage.bin) must never be flashed at 0x0 — they are OTA payloads, meant for POST /api/ota and POST /api/ota/webui. When in doubt, use a merged image at 0x0. Local files carry no checksum, so nothing can be verified for you here.

2 · Connect & flash

Plug the board's native USB port (USB-Serial/JTAG) into this computer with a cable that carries data — a charge-only cable shows no port at all. If the board does not appear in the port list, force the ROM bootloader (the "BOOT dance"):

  1. Unplug the board from your computer.
  2. Hold the BOOT button down (on some boards it is labelled 0 or IO0).
  3. Still holding it, plug the USB cable in — use the board's native USB / OTG socket if it has two.
  4. Release BOOT. The board is now in download mode and shows up as a USB-JTAG/serial device.
  5. Already plugged in? Hold BOOT, tap RESET (RST/EN), release BOOT — same effect.
Let go of BOOT once the board is plugged in. BOOT is not "flash mode" — it is held only across the moment of power-up or reset. If you keep it pressed, or wedge it down, the chip re-enters the ROM download loader on every boot and the firmware you just wrote never runs. The flash succeeds, the board looks dead, and there is no error anywhere to tell you why. This cost the author an afternoon. Same trap after flashing: the board resets into your firmware only if BOOT is free.

starting …

Flashed. Here is what happens next:

  1. Make sure BOOT is not held, then let the board reset (unplug and replug if it does not restart on its own).
  2. The device boots with no Wi-Fi configured and raises a recovery hotspot named Klingelbox-XXXX (the last two bytes of its MAC address), open, on channel 1.
  3. Join that hotspot from a phone or laptop — the captive portal opens the Wi-Fi wizard automatically. If it does not, browse to http://192.168.66.1.
  4. Enter your home Wi-Fi. The device reboots onto your network and is then reachable at http://klingelbox.local.

If the board seems dead after flashing, unplug and replug the USB cable — the USB-Serial/JTAG port can re-enumerate silently after a reset.

Log

Erase flash

Blanks the entire chip — firmware, Wi-Fi credentials, MQTT settings, every learned signal and the whole node graph are gone for good. Useful when a board is in a state you no longer trust. The chip itself cannot be bricked by this: its ROM bootloader is in mask ROM and is permanent, so a blank chip always comes back in download mode and can be reflashed here.

When something goes wrong

The port list in the browser prompt is empty

Either the cable is charge-only, or the board is not in download mode. Try a different USB cable first — it is the single most common cause. Then redo the BOOT dance above. On Linux, your user also needs access to the device node (typically membership of the dialout group, then log out and back in).

"Failed to connect" / the connection stalls

The board is powered but not listening. Redo the BOOT dance and press Connect & flash again. If another program holds the port — a serial monitor, the Arduino IDE, idf.py monitor, ESPHome — close it: only one process can own a serial port at a time.

"Checksum mismatch" or "size mismatch"

The download did not arrive intact, so the page refused to write it. That is the intended behaviour — a truncated image at offset 0x0 leaves a board that cannot boot and cannot tell you why. Reload the page (bypassing the cache with Ctrl/Cmd+Shift+R) and try again.

It flashed successfully but the board does nothing

Check that BOOT is not still held or jammed — see the warning above; that keeps the chip in the ROM download loader forever. Otherwise unplug and replug the cable. If it still does nothing, attach a serial monitor at 115200 baud and read the boot log; a wrong image for the board (a 16 MB image on a 4 MB ESP32-S3 Zero, say) shows up there as a partition-table or SPIFFS mount failure.

Can I brick the board from this page?

No. The ESP32-S3's first-stage bootloader lives in mask ROM and cannot be overwritten, so whatever is (or is not) in flash, the BOOT dance always brings the chip back into download mode. There is no sequence on this page that makes a board unrecoverable.
